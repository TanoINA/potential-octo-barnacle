# Native desktop integration

- Normal native launch registers `alt+space` through Rune on only the primary window. Secondary windows, `--smoke`, and all Rune headless runs never register a real shortcut. Headless runs deliberately skip virtual registration too.
- The shortcut restores/activates the same window and toggles its existing native History panel. It preserves the composer draft, conversation, and native key-handler focus (falling back to the composer) for modal focus return. This is not full SpotlightBar parity: there is no separate floating Spotlight window, cross-application focus restoration, or provider invocation.
- Rune at revision a7f276c has no `on_shortcut_error`; `take_shortcut_errors` is drained once each shell poll and reported through the visible shell error banner. Wayland shortcut activation tokens are forwarded to the same window's `activate` handle. Window-manager focus policy still applies.
- The controller exposes at most 32 successful acknowledged completions, including offscreen sessions. Failed/cancelled runs do not notify. A failed final save retains its pending completion for an explicit successful save/recovery. Completion events contain only session/run identifiers. The desktop host drains them once per poll, remembers the last 128 identities, and uses current persisted settings without changing defaults (`notifications_enabled=true`, `sound_chime_enabled=false`). Events observed while disabled are not replayed when enabled later.
- Native effects use one lazily started worker with a two-job queue; overflow is a visible error, not an unbounded backlog. The worker wakes Rune to surface failures. Notifications and sound are independent: one failure does not suppress the other. No speech or microphone capture is implemented.
- `rune-notify` uses the same pinned Rune git revision. Windows registers the app identity lazily on the first enabled notification, then posts an OS toast. That registration writes the application's own per-user notification identity registry key. There is no protocol-handler installation. macOS requires a bundled app and notification permission. Rune reports macOS post acceptance asynchronously and does not expose delivery/permission failures; acceptance is not proof a person saw a notification. Linux is explicitly unsupported by this Rune notification backend and produces a visible unavailable error. OS notification policy / Do Not Disturb can suppress presentation.
- Toast body is always `Task complete`, with no conversation contents, title, filename or path. Toast click navigation is not wired in this primitive.
- Chime playback uses rodio 0.21/CPAL's default output device and a generated quarter-second quiet two-tone PCM buffer. It runs off the UI thread with no files, processes, recording or network. Audio is opt-in only. Device-open errors surface visibly. Windows/macOS use native audio; Linux source builds additionally require ALSA development libraries.

## Verification and manual acceptance

Automated desktop tests use mock completion sinks or disabled desktop state. They test registration policy, once-only bounded dispatch, independent sound/notification flags, visible errors, History toggling with same-window callbacks, offscreen inbox draining, and quiet finite PCM generation without opening audio devices. Controller tests inject save acknowledgments, verify background completions, and suppress failed/cancelled/save-error events. No automated test grabs global Alt+Space, writes notification registration, posts toasts, or plays audio.

For manual native acceptance, launch with a disposable profile on an explicitly chosen interactive desktop. Check Alt+Space from another application and press it again to close History; confirm no draft is sent and the composer/key-handler focus is restored. With `--two-windows`, only the first window owns the shortcut. An existing Alt+Space owner must yield a visible error. Complete a real successful task in a background chat and check the generic toast; then explicitly enable the saved chime setting before checking sound. Disable each setting independently. Verify cancellation/error/final-save failure produces no completion effect. Do not run these interactive OS checks automatically or against the user's primary desktop.
